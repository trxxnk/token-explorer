# Архитектура

## Общая схема

```
браузер: index.html ──HTTP/SSE──► один из серверов
                                   ├─ LM Studio      /v1/responses, /v1/chat/completions
                                   ├─ OpenAI-совм.   /v1/completions (raw-промпт)
                                   ├─ llama-server   /completion (raw-промпт)
                                   └─ server.py      /generate (свой протокол)
```

Интерфейс ничего не знает о моделях: он шлёт запрос, получает поток токенов с вероятностями и хранит их. Различия протоколов спрятаны в трёх функциях: `streamCompletion()`, `streamLMS()`, `streamExplorer()`.

## Интерфейс

### Кто применяет шаблон чата

- **Raw-протоколы** (`openai`, `llamacpp`): шаблон (ChatML, Llama 3, Gemma) применяет клиент, на сервер уходит готовый текст промпта. Продолжение ответа — это тот же промпт плюс начало ответа.
- **LM Studio** (`responses`, `chat`): шаблон применяет сервер. Продолжение — незавершённое сообщение ассистента последним в списке.
- **Свой сервер** (`explorer`): шаблон модели применяет сервер, продолжение передаётся списком id токенов.

### Хранение

Всё лежит в `localStorage` браузера:

- `te.settings` — настройки; поле `v` — версия формата для миграций. Среди прочего: `tab_tokens` — шаг генерации (0 — весь ответ), `panel` — открыта ли панель настроек.
- `te.db` — `{ chats, order, current }`.

Чат — дерево узлов:

```
chat = { id, title, created, nodes: { root, <id>: node, ... } }
node = { id, parent, children: [id], active: <индекс активного ребёнка>, role, ... }
```

- узел пользователя: `text`;
- узел ассистента: `tokens[]`, `status` (`gen`/`done`/`error`), `params` (сэмплеры, модель и протокол на момент генерации), `stats`, `srv` (число токенов промпта, сколько взято из кэша, размер словаря), `thinkOff`, `branch`, `stopped`, `full`.

Видимая переписка — путь от корня по активным детям (`pathNodes()`). Ветка — новый узел-сосед с тем же родителем; `branch` хранит позицию и замену.

### Токен

```
{ t, p, top: [{ t, p, ... }], np, special }
```

| Поле | Значение |
|---|---|
| `t` | текст токена; может быть пустым, если токен — часть многобайтового символа |
| `p` | вероятность у модели (до сэмплеров) |
| `top` | кандидаты, по убыванию вероятности |
| `np` | вероятностей нет |
| `special` | служебный токен, рисуется плашкой |
| `b` | байты токена (LM Studio, llama.cpp) |
| `manual` | вставлен вручную или выбран пользователем |
| `r` | токен размышлений LM Studio (без вероятностей) либо синтетический тег `<think>` |
| `id` | id токена в словаре (свой сервер) |
| `q` / `cut` | шанс после сэмплеров либо имя сэмплера, который отсёк токен |
| `rank`, `H` | место в словаре и энтропия по всему распределению |
| `n` | сколько кандидатов осталось после top-k, top-p, min-p |
| `m`, `top[].k`, `top[].pp` | данные для показа вероятностей на каждом этапе отбора, см. [server-protocol.md](server-protocol.md) |
| `end` | токен конца ответа; не входит в текст ответа |
| `syn` | часть промпта (открывающий `<think>`), в префикс не отправляется |

### Окно токена

`openPop()` рисует два вида одного окна: короткую карточку при наведении и полную панель по клику.

- `verdict()` — цветная метка и одна фраза о токене.
- `stagesFor()` — цепочка этапов отбора. Каждый этап знает, сколько токенов осталось и какую вероятность имеет кандидат в этот момент; из тех же данных строятся формула и пример.
- На каждом этапе строки сортируются по текущей вероятности, новое место анимируется приёмом FLIP (запомнить старое положение, переставить, плавно доехать); числа и полосы доезжают до новых значений за секунду.
- `fetchMore()` — подгрузка следующих 25 кандидатов: тот же токен заново оценивается сервером с длинным списком. Результат хранится в памяти страницы, в чат не пишется.
- Этапы доступны только для токенов со своего сервера; для остальных протоколов панель показывает кандидатов и показатели без цепочки.

## Свой сервер

### Слои

- **`MLXBackend`** — всё, что зависит от движка: загрузка модели, шаблон чата, токенизация, прямой проход, кэш. Второй бэкенд (PyTorch) должен повторить этот интерфейс: `load`, `render`, `encode`, `decode`, `label`, `prime`, `step`, `eos`, `info`.
- **`analyze()`** — один шаг сэмплинга на numpy. Не зависит от движка: на входе логиты, на выходе выбранный токен и полное описание решения.
- **`Engine`** — очередь заданий и один рабочий поток, цикл генерации, выбор модели.
- **`Handler`** — HTTP: `/` (отдаёт `index.html`), `/v1/models`, `/info`, `/generate` (SSE).

### Кэш и снимки

Повторно считать весь промпт на каждый запрос дорого (Bonsai обрабатывает 10–20 токенов промпта в секунду). Обычный приём — обрезать кэш до нужной позиции — здесь не работает: в Qwen3.5 три слоя из четырёх рекуррентные и хранят состояние, которое нельзя отмотать.

Поэтому `prime()` хранит снимки кэша в двух точках:

1. конец последнего сообщения диалога — от него стартует следующий ход;
2. конец промпта без последнего токена — от него стартуют все ветки этого ответа.

На новый запрос выбирается самый длинный подходящий источник: живой кэш (если запрос его продолжает) или снимок. Хранится до 8 снимков.

### Точность

Модели в bfloat16 при загрузке переводятся в float32. Причина и измерения — в [problems-solved.md](problems-solved.md).

### Сэмплинг

Порядок как в llama.cpp: штраф за повторы (последние 64 токена) → top-k → top-p → min-p → temperature. Каждый этап оставляет начало отсортированного списка кандидатов, поэтому судьба токена определяется его позицией в этом списке. Без top-k словарь сортируется только на глубину 2048, полная сортировка — лишь когда этого не хватает.
