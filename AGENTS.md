# AGENTS.md

Правила и контекст для ИИ-агентов, которые работают с этим репозиторием. Описание проекта для людей — в [README.md](README.md), подробности — в [docs/](docs/).

## Что это за проект

Token Explorer — чат над локальной LLM для изучения выбора токенов. Две части:

- `index.html` — весь интерфейс: разметка, стили и скрипт в одном файле.
- `server.py` — необязательный сервер с собственным циклом генерации на MLX.

Интерфейс обязан работать без `server.py` (с LM Studio и llama.cpp). Сервер — дополнение, а не зависимость.

## Жёсткие правила

1. **`index.html` остаётся одним файлом без зависимостей.** Никаких библиотек, CDN, сборки, внешних шрифтов и скриптов.
2. **Всё ставится в окружение проекта.** Пакеты — только в `.venv`, веса — только в `./models`. Системный Python и глобальные пакеты не трогать.
3. **`server.py` использует стандартную библиотеку плюс `mlx-lm` и `numpy`.** Новая зависимость — только с согласия пользователя; тогда обновить `requirements.txt`.
4. **`.venv/`, `models/` не коммитить.** Скачивание моделей и установку пакетов согласовывать с пользователем, называя имя и размер.
5. **Язык.** Интерфейс, документация и общение с пользователем — на русском. Комментарии в коде — на английском, как сейчас.
6. **Объяснения простым языком.** Пользователь не специалист по внутренностям инференса: термин сопровождать практическим следствием.
7. **Не полагаться на документацию LM Studio.** Она расходится с поведением сервера; проверять `curl` к `localhost:1234`. Измеренное — в [docs/lm-studio-api.md](docs/lm-studio-api.md).

## Как запускать и проверять

- Сервер: `.venv/bin/python server.py`, затем http://localhost:8090.
- Node на машине нет: синтаксис скрипта `index.html` проверяется только загрузкой страницы в браузере.
- Страница, открытая в браузерной панели агента как `file://`, отображается статическим снимком и не делает запросов. Проверять через `http://localhost:8090` (сервер сам отдаёт `index.html`).
- Функции и состояние страницы — глобальные (`settings`, `db`, `chat()`, `send()`, `branchAt()`, `continueLast()`, `pathNodes()`, `tokensText()`), ими удобно управлять из консоли.
- **Пользователь сам работает в браузерной панели по адресу `localhost:8090`, там лежат его чаты.** Перед проверкой сохранить `te.db` и `te.settings` (например, в `sessionStorage`), после — удалить только созданные при проверке чаты и вернуть настройки. Никогда не очищать `localStorage` целиком.
- Движок можно гонять без HTTP: `server.Engine(server.MLXBackend()).generate({...})` возвращает генератор событий.
- После правки `server.py` запущенный сервер нужно перезапустить. Перезапуск сервера не перезагружает уже открытую вкладку: после правок `index.html` перейти на адрес заново.
- Автотестов нет. Минимальная ручная проверка после изменений: генерация, ветка от кандидата, свой текст, перегенерация с позиции, Tab, второй ход диалога, ответ с размышлениями.

## Карта кода

`index.html`, секции скрипта отмечены комментариями `/* ---------- имя ---------- */`:

| Секция | Содержимое |
|---|---|
| utils, state | помощники, настройки (`DEFAULTS`, миграции `settings.v`), дерево чата |
| chat templates | шаблоны ChatML/Llama3/Gemma для raw-протоколов |
| server I/O | `sse()`, `streamCompletion()` (raw), `streamLMS()`, `streamExplorer()`, `checkConnection()` |
| generation | `generate()`, `send()`, `branchAt()`, `continueLast()` |
| heat, rendering, popover | тепловая карта, отрисовка сообщений, окно токена (`verdict()`, `stagesFor()`, `fetchMore()`, `openPop()`) |
| settings drawer, composer, boot | настройки, ввод, клавиши, запуск |

`server.py`: `MLXBackend` (модель, токенизатор, кэш и его снимки), `analyze()` (один шаг сэмплинга с полным описанием решения), `Engine` (рабочий поток, цикл генерации), `Handler` (HTTP и SSE).

## Инварианты, которые легко сломать

- **Токен на клиенте** — объект `{t, p, top[], np, ...}`. Необязательные поля: `id`, `q`/`cut`, `rank`, `H`, `n`, `m`, а у кандидатов `k` и `pp` (свой сервер), `manual` (вставлен), `end` (токен конца), `syn` (часть промпта), `r` (размышления LM Studio без вероятностей), `b` (байты). Подробно — в [docs/architecture.md](docs/architecture.md).
- **Сравнение токенов** — через `same(a, t)` (по `id`, если есть), а не по тексту: фрагменты одного символа выглядят одинаково.
- **Текст ответа** собирать через `tokensText()`: он склеивает байты и пропускает токен конца.
- **Продолжение на своём сервере идёт по id токенов**, а не по тексту. Синтетические токены (`syn`) и токен конца в префикс не попадают.
- **Вся работа с MLX — в одном потоке** (`Engine._work`). Массивы MLX привязаны к потоку, в котором созданы.
- **Кэш модели нельзя «отмотать»**: у Qwen3.5 большинство слоёв рекуррентные. Вместо этого — снимки кэша (`prime()`, `marks`).
- **Модели в bfloat16 при загрузке переводятся в float32**, иначе ветка не воспроизводит исходные вероятности.
- **Порядок сэмплеров** как в llama.cpp: штраф за повторы → top-k → top-p → min-p → temperature.
- **Шаг генерации** (`settings.tab_tokens`, 0 — выключен) применяется в `generate()` ко всем запросам, а не только к Tab.
- **Панель токена не должна менять размер** при переключении этапов и не должна закрывать сам токен: блок объяснения и список кандидатов имеют фиксированную высоту, положение считает конец `openPop()`.
- **Кандидаты сверх сохранённых** подгружаются `fetchMore()` и живут только в памяти (`moreCache`); в чат их не записывать — хранилище ограничено.
- **Формат настроек менять через миграцию** (`settings.v`), у пользователя есть сохранённые настройки.
- **Протокол `/generate`** описан в [docs/server-protocol.md](docs/server-protocol.md); при изменении обновлять документ и обе стороны.

## Документация

При заметных изменениях обновлять:

- `README.md` — возможности, запуск, ограничения;
- `docs/decisions.md` — новое решение и его причина;
- `docs/problems-solved.md` — найденная и исправленная проблема;
- `docs/roadmap.md` — сделанное убрать, новые идеи добавить;
- `docs/architecture.md` и `docs/server-protocol.md` — при изменении формата данных, полей токена или протокола;
- этот файл — при появлении нового правила или инварианта.

## Git

Коммиты и отправка на GitHub — по просьбе пользователя. Сообщения на русском, в повелительном или назывном стиле, с пояснением «зачем».

**Перед каждым коммитом — обязательная проверка:**

1. Просмотреть весь diff (`git status`, `git diff`) и вспомнить, что обсуждалось и решалось по ходу работы.
2. Оценить важность каждого изменения и решения: что изменило поведение, протокол, формат данных, правила работы; от каких вариантов отказались и почему; какие проблемы нашлись и как решены.
3. Убедиться, что всё важное отражено в документации (см. раздел «Документация») и что документация не описывает того, чего в коде уже нет. Недостающее дописать до коммита, в тот же коммит.
4. В сообщении коммита перечислить важное, а не каждую правку.
