# Архитектура

## Общая схема

```
браузер: интерфейс (ui/dist) ──HTTP/SSE──► server.py
                                            ├─ /            файлы интерфейса
                                            ├─ /generate    генерация по токенам (поток)
                                            └─ /score       один проход без генерации
```

Интерфейс ничего не знает о моделях: он шлёт запрос, получает токены с вероятностями и хранит их. Шаблон чата применяет сервер; продолжение ответа передаётся списком id токенов.

Первая версия интерфейса была одним файлом `index.html` и умела работать с LM Studio и llama.cpp. Она удалена (см. [decisions.md](decisions.md)) и осталась в истории git; как ведут себя эндпоинты LM Studio, записано в [lm-studio-api.md](lm-studio-api.md).

## Интерфейс

Исходники — в `ui/`, сборка — `npm run app` (в `ui/dist`).

| Файл | Что в нём |
|---|---|
| `ui/src/` | компоненты дизайн-системы и `styles.css`; о сервере и состоянии не знают |
| `ui/app/logic.ts` | расчёты без React и сети: этапы отбора, вердикты, подсветка, промпт выбора |
| `ui/app/store.ts` | состояние, хранилище браузера, запросы к серверу, перенос данных прежней версии |
| `ui/app/main.tsx` | экраны «Генерация текста» и «Классификация текста», правая панель настроек; плавающая панель токена |

Состояние — один изменяемый объект `state` в `store.ts`. После изменения вызывается `bump()`, и экран перерисовывается (подписка через `useSyncExternalStore`). Во время генерации токены добавляются в узел, а перерисовка идёт не чаще кадра.

### Хранение

Всё лежит в `localStorage` браузера:

- `te2.settings` — настройки; поле `v` — версия формата для будущих миграций.
- `te2.db` — `{ chats, order, current: { chat, choice, last } }`: у каждого режима свой открытый чат (`null` — новый), `last` — выбранный режим.
- `te2.migrated` — отметка, что данные прежней версии уже перенесены.

Прежняя версия хранила данные под ключами `te.db` и `te.settings`. При первом запуске новая копирует оттуда чаты и настройки; старые ключи только читаются и остаются на месте.

Чат — дерево узлов:

```
chat = { id, title, created, updated, nodes: { root, <id>: node, ... } }   // updated — время последнего запроса
node = { id, parent, children: [id], active: <индекс активного ребёнка>, role, ... }
```

- узел пользователя: `text`;
- узел ассистента: `tokens[]`, `status` (`gen`/`done`/`error`), `params` (сэмплеры и модель на момент генерации), `stats`, `srv` (число токенов промпта, сколько взято из кэша, размер словаря), `thinkOff`, `branch`, `stopped`, `full`.

Видимая переписка — путь от корня по активным детям (`pathNodes()`). Ветка — новый узел-сосед с тем же родителем; `branch` хранит позицию и замену.

### Токен

```
{ t, id, p, q | cut, rank, H, n, m, top: [{ id, t, p, k, pp, q | cut }], special }
```

| Поле | Значение |
|---|---|
| `t`, `id` | текст и id токена в словаре; текст может быть пустым, если токен — часть многобайтового символа |
| `p` | вероятность у модели (до сэмплеров); `null` — вероятности нет |
| `q` / `cut` | шанс после сэмплеров либо имя сэмплера, который отсёк токен |
| `rank`, `H` | место в словаре и энтропия по всему распределению |
| `n` | сколько кандидатов осталось после top-k, top-p, min-p |
| `m`, `top[].k`, `top[].pp` | данные для вероятностей на каждом этапе отбора, см. [server-protocol.md](server-protocol.md) |
| `top` | кандидаты по убыванию вероятности |
| `special` | служебный токен, рисуется плашкой |
| `manual` | вставлен вручную или выбран пользователем |
| `end` | токен конца ответа; не входит в текст ответа |
| `syn` | часть промпта (открывающий `<think>`), в префикс не отправляется |

В чатах, перенесённых из прежней версии, встречаются токены без `id` и этапов (ответы LM Studio) и поля `np`, `r`, `b`. Такие токены показываются с кандидатами, но без цепочки этапов; ветка от них продолжается по тексту.

### Классификация текста (выбор из вариантов)

Чат с `kind: 'decision'` вместо дерева сообщений хранит:

```
chat.form = { instruction, question, options: [текст], labels: 'num'|'lat'|'cyr', prefix, template, line }
chat.runs = [{ id, created, form: <копия формы>, status: 'run'|'done'|'error', result, check }]
result    = { opts: [{ label, one, mass, final, toks }], inside, other, prompt, vocab, H, seconds, promptTokens, model }
check     = { rot: [[итог по вариантам в исходном порядке] для каждого сдвига], bias: [итог по меткам без содержания] }
```

- `one` — вероятность самого частого написания метки, `mass` — сумма по всем написаниям, `final` — доля среди вариантов; `inside` — сколько вероятности пришлось на все варианты вместе.
- Форма — черновик следующего прогона; каждый прогон хранит свою копию, поэтому карточки не меняются при правке формы. Пока у вопроса нет прогонов, форма живёт в памяти и чат не создаётся.
- `runChoice()` делает один запрос `/score`; `checkChoice()` — циклические сдвиги вариантов и проход с пустым содержанием.

### Панель токена

- `tokenVerdict()` — тон и фраза о токене; формулировки — из таблицы вердиктов в руководстве дизайн-системы.
- `stagesFor()` — цепочка этапов: каждый знает, сколько токенов осталось и какую вероятность имеет кандидат в этот момент. `stageRows()` раскладывает кандидатов этапа на оставшихся и отсечённых именно здесь.
- `fetchMore()` — следующие 25 кандидатов: тот же токен заново оценивается сервером с длинным списком. Результат живёт в памяти страницы, в чат не пишется.
- `Float` в `main.tsx` держит карточку и панель рядом с токеном: под ним, над ним или сбоку, не закрывая его. Состояния окна: `hover` — карточка, пока указатель на токене или на ней (уход — закрытие через 260 мс); `hold` — карточка остаётся, пока вводится своё слово; `panel` — полный разбор. `TokenCard` — карточка с тремя действиями, `TokenDetails` — панель.

## Свой сервер

### Слои

- **`MLXBackend`** — всё, что зависит от движка: загрузка модели, шаблон чата, токенизация, прямой проход, кэш. Второй бэкенд (PyTorch) должен повторить этот интерфейс: `load`, `render`, `encode`, `decode`, `label`, `prime`, `step`, `eos`, `info`.
- **`analyze()`** — один шаг сэмплинга на numpy. Не зависит от движка: на входе логиты, на выходе выбранный токен и полное описание решения.
- **`Engine`** — очередь заданий и один рабочий поток, цикл генерации, выбор модели.
- **`Handler`** — HTTP: `/` и файлы интерфейса из `ui/dist`, `/v1/models`, `/info`, `/generate` (SSE), `/score`.

### Кэш и снимки

Повторно считать весь промпт на каждый запрос дорого (Bonsai обрабатывает 10–20 токенов промпта в секунду). Обычный приём — обрезать кэш до нужной позиции — здесь не работает: в Qwen3.5 три слоя из четырёх рекуррентные и хранят состояние, которое нельзя отмотать.

Поэтому `prime()` хранит снимки кэша в двух точках:

1. конец последнего сообщения диалога — от него стартует следующий ход;
2. конец промпта без последнего токена — от него стартуют все ветки этого ответа.

На новый запрос выбирается самый длинный подходящий источник: живой кэш (если запрос его продолжает) или снимок. Хранится до 8 снимков.

### Точность

Модели в bfloat16 при загрузке переводятся в float32. Причина и измерения — в [problems-solved.md](problems-solved.md).

### Сэмплинг

Порядок как в llama.cpp: штраф за повторы (последние 64 токена) → top-k → top-p → min-p → temperature. Каждый этап оставляет начало отсортированного списка кандидатов, поэтому судьба токена определяется его позицией в этом списке. Без top-k словарь сортируется только на глубину 2048, полная сортировка — лишь когда этого не хватает.
